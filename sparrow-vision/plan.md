# sparrow-vision v1 实现计划

## 概要

实现一个 Tauri + React 桌面端日麻算番应用：用户上传牌桌照片后，程序使用 `ml/model/last.onnx` 识别牌面，按“用户手牌在画面底部”的默认构图自动分组，用户可修正识别结果和副露结构，然后通过 `riichi-calc` 计算役种、番数、符数和最终得点。

## 关键改动

- 新增 Rust Tauri 命令：
  - `recognize_image(image_bytes) -> recognition_result.v1`
  - `analyze_hand(request) -> scoring-result.v1`
- 新增算番请求数据结构，包含：
  - 手牌、副露、和了牌
  - 自风、场风、荣和/自摸
  - 立直/双立直、一发、抢杠、岭上、海底、河底、天和/地和相关状态
  - 本场数、宝牌指示牌、里宝牌指示牌
- 在 Rust 端集成 ONNX 推理：
  - 模型为 Ultralytics YOLO detect
  - 输入 `images`，输出 `output0`
  - 输入尺寸 `1280x1280`
  - 类别顺序与 `shared/specs/tile_vocab.v1.json` 一致
  - 默认阈值：置信度 `0.25`，NMS IoU `0.45`，最多保留 `32` 个检测框
- 将识别牌 ID 映射到 `riichi-calc`：
  - `m/p/s` 映射到万/筒/索
  - `m5r/p5r/s5r` 映射为赤五
  - `z1-z4` 映射为东南西北
  - `z5-z7` 映射为白发中
  - `f1-f8` 可以显示为识别结果，但 v1 不参与算番
- 将 `riichi-calc` 作为 Rust git 依赖接入，并把应用输入转换为 `PiInput + Field + Status`。
- 宝牌和里宝牌在 UI 中按“指示牌”输入，后端转换为实际宝牌后再调用 `riichi-calc`。

## UI 流程

- 首屏就是可用工具界面：
  - 图片上传/拖拽区域
  - 原图预览与检测框
  - 识别牌编辑区
  - 算番设置区
  - 结果展示区
- 识别后自动处理：
  - 按检测框位置排序
  - 将画面底部或最大横向牌组推断为手牌
  - 将其他分离牌组推断为副露候选
  - 低置信度、冲突或无法判断的牌进入“待确认”
- 用户修正能力：
  - 使用 CSS 文字牌块展示牌面
  - 可修改牌种、删除牌、添加牌
  - 可在手牌、副露、待确认之间移动牌
  - 可手动标记和了牌
  - 副露可标记为吃、碰、明杠、暗杠
- 算番设置：
  - 自风、场风
  - 荣和/自摸
  - 立直/双立直
  - 一发、抢杠、岭上、海底、河底、天和/地和类首巡自摸
  - 本场数
  - 宝牌指示牌、里宝牌指示牌
- 结果展示：
  - 是否和牌
  - 役种列表
  - 总番、符数
  - 荣和点数或自摸时庄家/闲家支付
  - 输入错误或算番错误提示

## 测试计划

- Rust 单元测试：
  - 牌 ID 到 `riichi-calc` 牌结构的转换
  - 赤五、字牌、宝牌指示牌转换
  - 牌数、和了牌、副露合法性、`f*` 非算番牌的校验
  - 平和立直荣和、简单自摸等已知算例
- 识别后处理测试：
  - YOLO 输出解析为检测框
  - NMS 去除重复框
  - 几何分组能把底部牌组归为手牌，不确定牌归为待确认
- 前端手动验收：
  - 上传图片、编辑识别结果、标记和了牌、设置状态、完成算番
  - 非法手牌能显示错误而不崩溃
  - 低置信度识别结果可以被用户修正
- 验证命令：
  - `cargo test`
  - `pnpm --filter sparrow-vision build`

## 默认假设

- v1 只做和了手牌算分，不做听牌/待牌分析。
- 默认照片构图是用户视角，自己的手牌位于画面底部，副露位于旁边分离区域。
- 自动分组是辅助功能，用户修正是正式流程的一部分。
- 识别和算番都在 Tauri Rust 后端执行。
- v1 使用 CSS 文字牌块展示牌面，后续可再替换成更精美的牌图资源。
